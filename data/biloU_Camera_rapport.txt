0. Governing Principle: Independent Approximation, Not Copying
================================================================================

0.1 Official Project Formula
---------------------------
Bilou Camera does not take and does not claim to take anything from Fujifilm. It is an independent
color engine providing an "approximation" of popular Film Simulation looks, built on:
  - Publicly published recipe settings from their authors (settings = facts about camera settings).
  - Open source models with clear licenses (MIT) describing a look with manually tuned parameters.
  - Our own custom visual tuning (Bilou native tuning) documented as an independent source.

The result is "close" and not "identical" — and may not be exactly the same at all. This is not a flaw
to hide; it is part of the product identity and must be visible in the UI, code, and App Store.

0.2 Strict Rules (Non-Negotiable)
---------------------------------
 1. No original Fujifilm LUTs, no proprietary RAF decoding, no internal parameters.
 2. Do not use terms like "Fujifilm LUT", "Authentic", "Exact", or "Identical".
 3. Every asset file (LUT/JSON) must have a manifest containing its source, license, and checksum.
 4. Do not ship any asset whose license is unclear (Section 1.4 clarifies this applies to current Fujilab LUTs).
 5. Every recipe retains its author's name, source, and link.
 6. Unknown values remain null and are not filled with default values.

0.3 Suggested UI Strings
------------------------
 AR: "مظهر مستوحى من أفلام Fujifilm — تقريب مستقل، وليس نسخة رسمية ولا مطابقة لها."
 EN: "Film-look inspired by popular Fujifilm recipes. An independent
      approximation — not an official or identical rendering."
 FR: "Rendu inspiré des recettes Fujifilm. Approximation indépendante —
      ni officielle, ni identique."
 Provenance badges in Recipe Inspector:
   [Published setting]  Published setting from recipe author
   [Community model]    Open community model (source + license)
   [Bilou native]       Custom parameter in our engine
   [Estimated]          Estimated
   [Not provided]       Not provided (null)

0.4 Trademark Note (Important Advice)
--------------------------------------
"Classic Chrome", "Classic Negative", "Film Simulation", and "Fujifilm" are names
associated with Fujifilm trademarks (this is a cautious estimate by me, not legal advice).
When shipping on the App Store, IP review may raise questions. I suggest:
  - Inside the code: You may keep identifiers classic-chrome / classic-negative
    for published recipe terms and metadata binding.
  - In the final user interface: Neutral names such as "Chrome (Bilou)" and
    "Negative (Bilou)" + an "inspired by" line.
  - Obtain a short legal review before public TestFlight.
  - No Fujifilm logos or images, and no official connection to the camera.

0.5 Internal Closeness Scale (Not a Marketing Claim)
------------------------------------------------------
Since your goal is a "very close ratio", we need a way to measure closeness without claiming identity.
I propose an internal scale for developers only (Section 3.9):
   Reference Closeness Score = Average ΔE00 between Bilou output and community
   reference output on a fixed standard color set.
Used for parameter tuning and regression detection, it is never shown to the user as an
"identical to Fujifilm" percentage because the reference itself (community LUT) is not original Fujifilm.

(D) How Fujilab Applies the LUT (from renderer.js) — Actual Processing Order
   1. 3D LUT (trilinear in hardware) with .bgr swizzle and scale/offset.
   2. Channel curves (256x3 texture).
   3. Color Chrome / FX Blue (HSV-hue space calculation).
   4. Highlights / Shadows (direct addition to values).
   5. Temperature / Tint (addition to R/G/B — after LUT).
   6. Saturation / Vibrance.
   7. Vignette.
   8. Grain (based on gl_FragCoord and hash, non-temporal).
   9. High-light desaturation (luma > 0.85) then clamp.

(E) Quality/Design Notes on Fujilab Code (Affecting Our Decisions)
   - No Input Transform: Image enters directly (sRGB/browser) into LUT.
     We must have an explicit conversion (Display P3 / HDR) — see 2.5.
   - White balance is applied after LUT additively in encoded (gamma) space
     rather than linear light multiplication. Blueprint (Sections 1.2 and 9) requires WB
     before LUT. => We do not copy this order.
   - Grain relies on gl_FragCoord/cellSize => size changes relative to resolution between preview
     and export. Ours must be resolution-independent.
   - Browser-bound and mostly limited to 8-bit; we work in float16 in Metal.
   - Color Chrome code relies on hard thresholds (sat > 0.15, hue < 200) — may cause
     abrupt transitions; Blueprint 9 warns against hard thresholds.
   - Shadow signal: See 1.5 (potential important signal inversion).

(F) Regarding Classic Negative in Fujilab
   - recipeParser.js (lines 46–48) maps "classic negative" and "classic neg"
   to a fallback: "Classic Chrome" with warning "Classic Negative approximated with Classic Chrome".
   => This is precisely the risk warned against by the blueprint (Risk: Classic Negative =
   Classic Chrome + adjustment). Fujilab falls into it. We prevent it via a
   validator rule (Section 4.8).
   - recipes.js: Number of recipes by filmSim: Classic Chrome 33, Pro Neg Std 6,
   Astia 2, Provia 2, one each for Acros, Mono+R, Pro Neg Hi, Velvia,

1.5 Warning: Shadow Tone Signal Direction (Potential Bug in Fujilab)
----------------------------------------------------------------------
- Per Fujifilm educational sources and forums: Positive Highlight Tone = brighter highlights;
  Positive Shadow Tone = darker shadows (inverted direction). Negative shadow = brighter shadows.
- In Fujilab: recipeParser sets adj.shadows = Math.round(val * 10) without inversion,
  and the shader adds (shadows/100 * 0.5 * sw^2) to color => positive value brightens
  shadows. This is the reverse of Fuji behavior (unless I misread the rest of the code).
- In Fuji Recipe Converter: curve[0.25] = 0.25 - shadow where shadow = positive
  value * 0.022 => positive darkens shadows, matching Fuji.
=> Our decision: Adopt Fuji convention (Shadow + = darker) as in Recipe Converter,
   and add a unit test proving it. This exemplifies why Fujilab constants cannot be copied as-is.

2. General Architecture / Conception of the Photo Pipeline
================================================================================

2.1 Design Principles (Decisions Governing Everything)
------------------------------------------------------
 P1. Film Simulation = independent base profile. Recipe = data layer above it.
     No "filter per recipe".
 P2. Three separate layers always: Source Settings (author's published) →
     Mapping (versioned mapping) → Native Parameters (executed by our engine).
 P3. Each processing stage has a "contract": input space, output space,
     parameters, neutral behavior (neutral = no change), and CPU test reference.
 P4. Base color = 3D LUT generated from a parametric model (Look Compiler). Spatial effects
     (grain, clarity, sharpen, NR) are separate kernels.
 P5. Preview and export use the same functions and LUT at two different resolutions
     (preview == export principle seen in Recipe Converter).
 P6. Nothing is "assumed": Every color space and device capability is read at runtime.
 P7. Determinism: Same (image + recipe + versions) = same output.
 P8. Honesty: Every asset and parameter carries provenance; nothing is called "Fujifilm".
 P9. Non-destructive export: Original is always saved, editing = data (JSON).
 P10. Core Image as coordinator + Metal as executor (Section 2.10) to minimize risks for a small team.

2.5 Color Management Policy — Most Important Architecture Decision (Proposed ADR-001)
------------------------------------------------------------------------------------
Problem: LUT without a known input space yields incorrect results. Fujilab passes pixels
to LUT as-is; Recipe Converter explicitly defines "display-referred sRGB/Rec.709".
With us, images from iPhone mostly arrive in Display P3 (sometimes HDR/gain map).

Proposed Decision:
  (1) Look Space v1 = Display P3 primaries + sRGB transfer function
      (i.e., Display P3 encoding used by Apple for display), display-referred,
      float16 precision allowing values outside [0,1] in non-LUT stages.
      Reason: Our LUT is generated from a parametric model (we own the definition),
      so the look can be defined directly in P3 space without clipping color gamut, and without
      needing an sRGB-measured LUT. sRGB images are converted to P3 losslessly.
  (2) All "light" stages operate in extended linear Display P3: Exposure (multiply
      by 2^EV), White balance (red/blue gains), light noise reduction.
  (3) Before LUT, encode to Look Space (apply sRGB transfer on linear P3),
      then apply LUT, then spatial stages.
  (4) Output: HEIC/JPEG in Display P3 with ICC, or sRGB (gamut conversion with
      soft clip) when "higher compatibility" is chosen.
  (5) HDR / gain map (modern HEIC): v1 produces SDR only. We read images with explicit
      tone-mapping to SDR (appropriate Core Image option, [VERIFY] current SDK
      name: toneMapHDRtoSDR / expandToHDR), and document that gain maps are not
      saved in output. We do not apply an SDR look to HDR values without explicit decision.
  (6) LUT manifest records lookSpace; reject loading LUTs that do not match lookSpace.
  (7) Alternative (if simplicity preferred): Look Space = sRGB as in Recipe Converter
      strictly, with P3->sRGB conversion before LUT. Easier to compare with references but
      clips P3 colors and makes images less vibrant on iPhones. I recommend (1).
  Note: Definition of color ranges (Red/Orange/...) follows look space; therefore
  parameters are visually retuned within the adopted space, recorded in the manifest.

2.6 Photo Render Graph — Adopted Order
--------------------------------------
 Inputs: HEIC / JPEG (v1), then RAW/ProRAW via Apple path (v1.5), then Live Photo
 still (v2).

 [S0] Decode + Orientation + Metadata        ImageIO / CIImage
 [S1] Colour-in: to extended linear Display P3
 [S2] Exposure (post) = linear multiplication (optional, user-controlled)
 [S3] Relative white balance (R/B shift as linear gains) + user temp/tint
 [S4] Light noise reduction (before look so shadow noise isn't contrast-amplified)
 [S5] Encode to Look Space (sRGB TRC on linear P3)
 [S6] LOOK LUT (generated: base simulation + tone + recipe color ops)
 [S7] Clarity (local contrast on luma, protected in shadows/highlights)
 [S8] Sharpening (on luma, per output resolution)
 [S9] Halation / Bloom / Vignette (optional, disabled by default)
 [S10] Grain (resolution-independent, fixed seed, luma-weighted)
 [S11] Output: gamut map -> light dither -> encode -> ICC -> file

 Deliberate deviation notes from Blueprint 7.5 order:
  - Blueprint puts NR with spatial effects (step 11). I move it before look
    (S4) because LUT/curve amplifies shadow contrast, thus amplifying noise. Blueprint itself
    says conceptual order may change. I keep it toggleable and visually measured.
  - Linear WB before LUT as requested by blueprint. (Fujilab and Recipe Converter
    both "bake" or apply WB after/inside LUT — we do not copy them here).
  - DR/Highlight/Shadow/Color/ColorChrome are baked inside LUT (S6) because they are
    pixel-level tone/color operations, but remain toggleable and editable because
    LUT is recomputed from parameters (2.7).

 Stage Table (Domain and Execution):
 +-----+-------------------+----------------+-------------+------------------+
 | ID  | Stage             | Domain         | Executed    | Toggleable       |
 +-----+-------------------+----------------+-------------+------------------+
 | S1  | Colour-in         | linear P3 ext. | fused kern. | No               |
 | S2  | Exposure          | linear P3      | fused kern. | Yes (0 EV)       |
 | S3  | White balance     | linear P3      | fused kern. | Yes (0,0)        |
 | S4  | Noise reduction   | linear/log     | CI/Metal    | Yes              |
 | S5  | Encode to look    | P3 + sRGB TRC  | fused kern. | No               |
 | S6  | Look LUT          | look space     | fused kern. | Yes (identity)   |
 | S7  | Clarity           | look (luma)    | Metal       | Yes              |
 | S8  | Sharpening        | look (luma)    | CI/Metal    | Yes              |
 | S9  | Halation/Vignette | linear/look    | Metal       | Yes (default off)|
 | S10 | Grain             | look (luma)    | Metal       | Yes              |
 | S11 | Output            | target space   | CI          | No               |
 +-----+-------------------+----------------+-------------+------------------+
 "fused kernel" = single kernel combining S1+S2+S3+S5+S6 to minimize memory reads.

2.7 Look Compiler (Component Not in Blueprint — Proposed Addition)
------------------------------------------------------------------
Function: Converts (Profile + Recipe Native Params + LookSpace + gridSize) into a
ready 3D LUT, then caches it.

 Input  : FilmSimulationProfile.lookModel + RecipeNativeParameters (tone/
          colour ops only) + lookSpace + gridSize (17/33/65)
 Process: For each node (r,g,b) in grid, call same LookTransform function:
          curve -> HSL band ops (hue/sat/lum) -> split-toning -> [color chrome]
 Output : 3D MTLTexture rgba16Float + parameter hash fingerprint.
 Cache  : Key = sha256(profileId, profileVersion, recipeId, recipeVersion,
          paramsHash, lookSpace, gridSize, engineVersion) — in-memory and on
          disk (Caches/). Recomputed only when key changes.
 Sizes  : Preview 33^3 (quick draft 17^3 during drag), export 65^3 (or 33^3 with
          tetrahedral). Cost: 65^3 = 274,625 nodes — very small for GPU; expected
          to be imperceptible but measured on device [measurement required].
 Exec   : CPU reference version (Swift) + Metal compute version of same function;
          tests compare both on fixed inputs.
 Benefit: Editing Highlight or Color Chrome via slider = fast re-bake, without
          extra shader kernel, and each recipe = single LUT => stable performance.

 Resolution Precision (Table): Initial 17^3 LUT with sharp curve data may show
 banding; hence 33^3 is minimum for preview, 65^3 for export.

2.9 Live Preview
----------------
 - AVCaptureVideoDataOutput (BGRA) at limited preview resolution (e.g. up to ~1080p, [measured]).
   (This is stream for preview only during photo stage; full video later.)
 - CVMetalTextureCache -> same fused kernel + same generated LUT (33^3) ->
   MTKView.
 - Spatial effects in Preview mode: grain at relative size (same look at 100%),
   clarity/sharpen at half resolution or disabled during motion.
 - Preview fidelity: Preview image does not pass Apple pipeline (Deep Fusion...), so
   final image may differ slightly; display actual image result immediately after capture
   with smooth transition, and document difference in Settings > About the look.
 - Any recipe change during preview = LUT re-bake (background) + atomic texture
   swap (no dropped frames).

2.10 Coordinator and Executor: Core Image + Metal
--------------------------------------------------
 Proposal: CIContext created with working space = extended linear Display P3 and
 workingFormat = RGBAh, graph built as CIImage graph:
   - LUT: CIColorCubeWithColorSpace (fast MVP path, trilinear), or custom Metal Core
     Image kernel for tetrahedral later.
   - Custom kernels (grain, clarity, halation) written in Metal Shading Language
     and loaded as CIKernel (benefiting from automatic tiling in Core Image).
   - NR/Sharpen: Ready CI filters first (CINoiseReduction, CINoiseReduction, CIUnsharpMask), then
     custom kernels if needed.
 Why? For a small team: Core Image provides tiling/memory/colour management out of the box
 and reduces Metal errors. We retain pure Metal compute option (fused kernel) for
 live preview and video later when tighter frame control is required.
 Risk: Core Image reorders operations internally and blends values between passes; hence
 each stage is tested against CPU reference comparison (Section 2.14).
 [VERIFY] CIColorCube cubeDimension size limit on target iOS before adopting 65^3.

2.12 Determinism
----------------
 - grainSeed = hash(assetId, recipeId) (fixed per image) — or "new seed"
   via UI tap.

   and 12MP/48MP export.

   measurement on actual devices; no preset assumed number.

3.4 LookTransform Design (Master Function)
--------------------------------------------
 Input : RGB encoded in Look Space (values may slightly exceed [0,1])
 Output: RGB in Look Space

 Steps (as in engine.js: makeTransform) — in order:
   1) [WB gains] In source, applied inside function in linear light. With us, not
      entered in LUT (S3 separate) — first intentional departure from source.
   2) Tone curve: Monotone cubic curve with 5 points:
        (0, lift) (0.25, 0.25 - shadow + lift*0.6) (0.5, 0.5)
        (0.75, 0.75 + high - roll) (1, 1)
      where shadow = shadowTone × 0.022 + sim.shadow , high = highlightTone ×
      0.022 + sim.high , roll = DR × 0.022 (see Section 5 for DR).
      Constraints in source: clamp(0.25 - shadow, 0.06, 0.4), clamp(0.75 + high -
      roll, 0.6, 0.93).
   3) For each chromatic pixel (chroma c > 1e-6): h = hue angle (HSV-style)
        - hue rotation: angle = bandValue(hue,h) × 0.3° (±100 ≈ ±30°)
          via rotation matrix around axis (1,1,1).
        - saturation: k = (1 + sat/100) × max(0, 1 + bandValue(satB,h)/100)
          then rgb = y + (rgb - y) × k
        - luminance per band: k = 1 + bandValue(lum,h)/100 × 0.9 × min(1, c×1.6)
      For gray (c≈0): general sat only is applied.
   4) Split toning: Shadow weight (1-y)^2, highlight weight y^2, global 4y(1-y), intensity
      sat/100 × 0.22, on tint vector with zero luma.
   5) clamp [0,1].

 bandValue(): Linear interpolation between 8 band centers (with 360° wrap).

3.5 What We Improve Over Source (Proposed Fixes and Enhancements)
------------------------------------------------------------------
 Versioning principle: ‘v1.0’ = parity with open model (for testing); ‘v1.1+’ = Bilou tuning.
 Both kept retrievable.
  F1  Luma parameters per look space: Source uses Rec.709 (0.2126, 0.7152,
      0.0722) because it's sRGB. Our Look Space = Display P3, so we use P3
      weights (approx 0.2290, 0.6917, 0.0793) derived from matrix, not memory.
  F2  Move WB outside LUT (before LUT, linear) — matching blueprint recommendation.
  F3  Extended floating values: No clamp in pipeline middle (source clips near 8-bit);
      clip once at output (soft gamut mapping).
  F4  Curve midpoints: 5 points give simple tone; add optional toe/shoulder points
      (7–9 points) as Bilou native parameters.
  F5  Black lift + shadow tint (see 3.6) as Bilou native parameters (lift RGB).
  F6  Highlight shoulder + smooth desaturation near white instead of hard thresholds
      (Fujilab does something similar at luma > 0.85).
  F7  LUT interpolation: Trilinear as base; tetrahedral for export.
  F8  Dither when writing to 8-bit to avoid gradient banding.
  F9  Experimental "OKLCH" version (v2): Perform band ops on OKLCH instead of HSV for
      smoother hue transitions. Built as a profile with different version, not replacement.
  F10 Input normalization: Clarity/NR/Grain never enter LUT (as is currently).

3.6 Gap Analysis — Actual Measured Numbers
-------------------------------------------
 Method: Ran engine.js (Recipe Converter) in Node to generate 17^3 LUT for
 Classic Chrome with neutral settings, and compared it with Fujilab file (Classic Chrome.3dl,
 17^3, B fastest) on same grid nodes using ΔE2000 metric (sRGB→Lab, skimage).
 ΔE2000: ≈1 barely noticeable, 2–3 small difference, 5+ clear difference.

   Look Strength (difference from identity):
     RC Classic Chrome model    : mean 5.20  median 5.01  p95 9.01  max 12.36
     Fujilab Classic Chrome     : mean 5.23  median 5.14  p95 7.94  max 12.72

     RC-CC vs Fujilab-CC        : mean 3.76  median 3.65  p95 7.41  max 9.48
     (Comparison: without any look vs Fujilab-CC: mean 5.23)
   => Raw model closes only about 28% of the gap. "Close in direction" but
      not "very close" yet. This is a sincere preliminary estimate.

   Neutral Axis (R=G=B) — Two clear differences:
     input 0.00 : RC=(0.000,0.000,0.000)  Fujilab=(0.038,0.042,0.046)
     input 0.25 : RC=(0.215,0.215,0.215)  Fujilab=(0.259,0.294,0.316)
     input 0.50 : RC=(0.500,0.500,0.500)  Fujilab=(0.518,0.523,0.526)
     input 0.75 : RC=(0.758,0.758,0.758)  Fujilab=(0.761,0.758,0.754)
     input 1.00 : RC=(1.000,1.000,1.000)  Fujilab=(0.999,0.999,0.985)
   Conclusion: Community reference (1) lifts blacks (matte), (2) tints shadows with
   blue/cyan bias (B>G>R), (3) leans slightly warm in high highlights. Recipe Converter
   model for Classic Chrome contains no lift and no split-toning (though its
   Classic Neg definition has grade: teal shadows hue 185 and warm highlights hue 45).

   Feasibility experiment: Applying gain+offset per channel (6 parameters only) over RC model
   dropped the mean from 3.76 to 2.25 (p95: 4.20). Meaning adding "black lift + shadow tint"
   alone bridges much of the gap. This guides F5 tuning above.

   - Reference LUT itself is unofficial and unclearly licensed. Using it as internal
   developer benchmark is less risky than numerically "fitting" our parameters on its
   data (data fitting), because the latter makes our parameters effectively derived from it.
   - My recommendation: (1) Use qualitative directions only (higher blacks, cooler shadows,
   warmer highlights) and tune by eye on our own test images; (2) Do not paste fit numbers in
   production; (3) If numerical fitting is desired, do so after permission/license or legal counsel;
   - Cleaner alternative: Calibration (Path C) on images we have rights to use.
   - The above experiment was run for analysis only and its values are not transferred to files.

5.4 Resolver: From Recipe to ResolvedLook
------------------------------------------
 effective = Mapper(source) ⊕ profileDefaults ⊕ userOverrides
 - userOverrides never modify source values (separate layer).
 - reset-to-source: drops overrides. reset-to-default: returns to profile defaults.
 - ResolvedLook = { profileRef, preLook{exposure,wb,nr}, lookParams{tone,
   colour,chrome,fxBlue,dr}, postLook{clarity,sharpen,grain,...}, warnings[] }
 - Warning examples: "WB preset ignored for non-RAW", "DR-P approximated",
   "Smooth Skin unsupported", "Value not provided".
 - Recipe switching creates a new ResolvedLook from scratch (no leakage).

5.5 Effect Modules
------------------
 Unified interface:
   protocol RecipeEffect {
     static var id: String { get }
     var stage: RenderStage { get }            // S3, S4, S6 ...
     var inputDomain: ColorDomain { get }
     var isNeutral: Bool { get }               // disabled = no effect
     func cpuReference(_ px: SIMD3<Double>, ctx: EffectContext) -> SIMD3<Double>
     func makeKernel(ctx: RenderContext) -> RenderKernel?
   }
 Per effect: parameter range, neutral behavior, Preview/Export quality, CPU reference,
 performance budget, relation to other stages (blueprint Phase 7 requirement).

 Proposed details:
 (1) WhiteBalanceEffect (S3): Linear multiplication by gains (before LUT). Note: R+5
     is not "5 RGB units"; relative shift converted via formula above and termed approx.
 (2) ExposureEffect (S2): Linear 2^EV. Optional (post); not driven by guidance.
 (3) Highlight/Shadow/DR: Inside LUT curve (S6) — monotone curve; ensures max value
     additions don't invert curve (clamp constraints like source).
 (4) Color: Saturation around neutral axis weighted by luma (reduces contamination in
     high highlights).
 (5) ColorChrome (S6): v1 = lum per range (RC). v1.1 proposed "OKLCH": lower luma
     proportionally to chroma C within smooth hue window: ΔL = -k × smoothstep(C)
     × w(h). Acts as "depth on saturated colors" rather than global saturation. (Blueprint
     description: selective-color operation, not global saturation.)
 (6) FXBlue (S6): Hue window around blue (cosine window width ~±55° around 235–250°
     as Fujilab does conceptually) with smooth roll-off; no hard thresholds. Note: Effect may
     vary across sensor generations (project file).
 (7) GrainEffect (S10): Multi-octave noise weighted by luma (stronger in shadows/mids),
     fixed seed, side-length scale, no gl_FragCoord. Monochrome grain as initial assumption.
 (8) ClarityEffect (S7): Large-radius high-pass on luma × midtone mask; negative = blend
     with blurred version (approximates but does not optically match ProMist filter —
     as project file states).
 (9) SharpeningEffect (S8): Unsharp on luma; radius tied to output resolution.
 (10) NoiseReductionEffect (S4): Light luma/chroma NR; photos only in v1.
 (11) Halation/Bloom/Vignette (S9): Outside the 8 recipes (not mentioned in them);
      deferred and disabled by default.

C.3 Monotone Curve (Fritsch–Carlson) — Translation of FR.makeCurve
-------------------------------------------------------------------
public struct MonotoneCurve {
    private let xs: [Double], ys: [Double], m: [Double]

    public init(points: [SIMD2<Double>]) {
        let xs = points.map { $0.x }, ys = points.map { $0.y }
        let n = xs.count
        var d = [Double](repeating: 0, count: n - 1)
        for i in 0..<(n - 1) { d[i] = (ys[i + 1] - ys[i]) / (xs[i + 1] - xs[i]) }
        var m = [Double](repeating: 0, count: n)
        m[0] = d[0]
        if n > 2 {
            for i in 1..<(n - 1) { m[i] = (d[i - 1] * d[i] <= 0) ? 0 : (d[i - 1] + d[i]) / 2 }
        }
        m[n - 1] = d[n - 2]
        for i in 0..<(n - 1) {
            if d[i] == 0 { m[i] = 0; m[i + 1] = 0; continue }
            let a = m[i] / d[i], b = m[i + 1] / d[i], s = a * a + b * b
            if s > 9 { let t = 3 / s.squareRoot(); m[i] = t * a * d[i]; m[i + 1] = t * b * d[i] }
        }
        self.xs = xs; self.ys = ys; self.m = m
    }

    public func value(_ x: Double) -> Double {
        if x <= xs[0] { return ys[0] }
        if x >= xs[xs.count - 1] { return ys[ys.count - 1] }
        var k = 0
        while x > xs[k + 1] { k += 1 }
        let h = xs[k + 1] - xs[k], u = (x - xs[k]) / h, u2 = u * u, u3 = u2 * u
        return (2*u3 - 3*u2 + 1) * ys[k] + (u3 - 2*u2 + u) * h * m[k]
             + (-2*u3 + 3*u2) * ys[k + 1] + (u3 - u2) * h * m[k + 1]
    }
}

C.4 LookTransform (CPU Reference) — The Core
--------------------------------------------
public struct LookTransform {
    let model: LookModel
    let curve: MonotoneCurve
    public init(_ model: LookModel) { self.model = model; self.curve = MonotoneCurve(points: model.curve) }

    public func apply(_ rgb: SIMD3<Double>) -> SIMD3<Double> {
        let w = model.lumaWeights
        // 1) tone curve per channel (+ optional Bilou black lift)
        var c = SIMD3(curve.value(rgb.x), curve.value(rgb.y), curve.value(rgb.z))
        c = c * (SIMD3(repeating: 1) - model.blackLift) + model.blackLift

        // 2) HSL-style band operations
        var y = (c * w).sum()
        let mx = max(c.x, max(c.y, c.z)), mn = min(c.x, min(c.y, c.z)), chroma = mx - mn
        let satK = 1 + model.saturation / 100
        if chroma > 1e-6 {
            let h = hueDegrees(c, mx: mx, mn: mn)          // computed once (as in source)
            let angle = bandValue(model.hue, h) * 0.3 * .pi / 180
            if angle != 0 { c = rotateAroundGrey(c, angle); y = (c * w).sum() }
            let k = satK * max(0, 1 + bandValue(model.satBands, h) / 100)
            c = SIMD3(repeating: y) + (c - SIMD3(repeating: y)) * k
            let kl = 1 + bandValue(model.lumBands, h) / 100 * 0.9 * min(1, chroma * 1.6)
            c *= kl
        } else {
            c = SIMD3(repeating: y) + (c - SIMD3(repeating: y)) * satK
        }

        // 3) split toning (zero-luma tint vectors)
        c = applySplitTone(c, model.split, w)
        return c            // NO clamp here: gamut handled once, at output (F3)
    }
}

func hueDegrees(_ c: SIMD3<Double>, mx: Double, mn: Double) -> Double {
    let d = mx - mn
    if d < 1e-9 { return 0 }
    var h: Double
    if mx == c.x { h = ((c.y - c.z) / d).truncatingRemainder(dividingBy: 6) }
    else if mx == c.y { h = (c.z - c.x) / d + 2 }
    else { h = (c.x - c.y) / d + 4 }
    h *= 60
    return h < 0 ? h + 360 : h
}

func bandValue(_ arr: [Double], _ h: Double) -> Double {
    let hues = LookModel.bandHues + [360]
    for i in 0..<8 where h <= hues[i + 1] {
        let t = (h - hues[i]) / (hues[i + 1] - hues[i])
        return arr[i] + (arr[(i + 1) % 8] - arr[i]) * t
    }
    return arr[0]
}

func rotateAroundGrey(_ c: SIMD3<Double>, _ v: Double) -> SIMD3<Double> {
    let cs = cos(v), sn = sin(v), o = (1 - cs) / 3, s3 = (1.0 / 3.0).squareRoot() * sn
    return SIMD3(c.x * (cs + o) + c.y * (o - s3) + c.z * (o + s3),
                 c.x * (o + s3) + c.y * (cs + o) + c.z * (o - s3),
                 c.x * (o - s3) + c.y * (o + s3) + c.z * (cs + o))
}

C.5 Baking LUT on CPU (For Testing and Reference)

// Output: RGB float triples, RED index varies fastest (same as .cube files).
public func bakeLUT(_ t: LookTransform, grid n: Int) -> [Float] {
    var out = [Float](); out.reserveCapacity(n * n * n * 3)
    let s = 1.0 / Double(n - 1)
    for b in 0..<n { for g in 0..<n { for r in 0..<n {
        let o = t.apply(SIMD3(Double(r) * s, Double(g) * s, Double(b) * s))
        out += [Float(o.x), Float(o.y), Float(o.z)]
    }}}
    return out
}

kernel void bakeLUT(texture3d<half, access::write> lut [[texture(0)]],
                    constant LookParams &p [[buffer(0)]],
                    uint3 gid [[thread_position_in_grid]])
{
    if (gid.x >= lut.get_width() || gid.y >= lut.get_height() || gid.z >= lut.get_depth()) return;
    float3 rgb = float3(gid) / float(lut.get_width() - 1);

    lut.write(half4(half3(o), 1.0h), gid);
}

Appendix D: Glossary
================================================================================
 Film Simulation   : Base look (here Chrome / Negative as independent approximation).
 Film Recipe       : Recipe = Film Simulation + Settings (published values).
 Look Space        : Color space where the look is defined and LUT applied.
 LUT 3D            : Table transforming each color (R,G,B) to a new color.
 Trilinear/Tetrahedral : Two interpolation methods between LUT nodes.
 Input/Output Transform : Transforming colors to/from working space.
 Display-referred  : Values relative to display (SDR) rather than linear scene-light.
 ΔE2000            : Visual color difference metric (≈1 barely noticeable).
 Oracle            : Reference implementation (here engine.js) against which we compare.
 Look Compiler     : Component transforming (profile+recipe) into a cached baked LUT.
 Provenance        : Record of origin (source, license, confidence, status).
 Capture-only      : Shooting setting (EC/ISO/WB preset) not applied as post-processing.
 Capture Assist    : Optional feature actually executing recipe guidance at capture.
 ProRAW            : Apple's computational RAW format (not standard Bayer DNG).
 Gain map HDR      : HEIC/JPEG images with gain map for HDR display.
 Determinism       : Same input + version = same output.
